# Put MAYA online with Render (free)

This gives MAYA its own public `https://` address. Judges then open it on their
own phones, from any network, without IP addresses or a laptop on the same
Wi-Fi. It uses the same approach as the earlier `maya-site` deployment: one
Docker web service on Render's free tier, described by a Blueprint file.

Unlike `maya-site`, no separate deploy repository is needed. The repository's
`Dockerfile` trains the small synthetic demo bundle during the image build
(about a minute), so no model weights are ever committed.

## One-time setup (about 10 minutes)

1. Sign in at <https://render.com> with GitHub and allow access to
   `ldcode20/MAYA-SAZI`.
2. **New → Blueprint**, pick `MAYA-SAZI`, then **Apply**. Render reads
   `render.yaml` and creates the `maya-sazi` web service.
3. Wait for the first build (5 to 10 minutes on the free tier). The site is at
   `https://maya-sazi.onrender.com`, or `https://maya-sazi-xxxx.onrender.com` if
   the name was taken. Render shows the exact address on the service page.
4. Check `https://<address>/readyz` shows `"status":"ready"`.

Pushes to `main` redeploy automatically (`autoDeploy: true`).

## What the Blueprint sets

| Setting | Value | Why |
|---|---|---|
| `MAYA_ENV` | `production` | Secure cookies, HSTS, no `/api/docs`. |
| `MAYA_SESSION_SECRET` | generated by Render | Signs sessions; never in Git. |
| `MAYA_OPERATOR_KEY` | generated by Render | Unlocks `/operator/`. Copy it from **Environment** on the service page. |
| `MAYA_TRUST_FORWARDED_FOR` | `1` | Rate limits use the right-most `X-Forwarded-For` entry, the one Render's proxy appends. Client-supplied entries are ignored. |
| `MAYA_REQUESTS_PER_MINUTE` | `1200` | Room for several phones and screens per visitor address. |

The public origin defaults to Render's own `RENDER_EXTERNAL_URL`. All
state-changing requests must come from that origin. With a custom domain, set
`MAYA_PUBLIC_ORIGIN=https://your.domain` in **Environment**.

## Running the demo on the public site

1. **Presenter's phone:** open `https://<address>/app/` and pick a situation
   (for example "After a “stock tips” group").
2. **Judge's phone:** on the payment screen, tap **Connect judge device**. The
   judge scans the QR with their phone camera, which opens `/demo/` already
   paired. Typing the 12-character code at `https://<address>/demo/` also works.
3. **Recipient screen (optional):** **Connect recipient device**, scan the same way.
4. When the presenter switches situation, paired judge and recipient screens
   follow automatically. Trusted-contact screens do not, because consent is
   given per situation.
5. **A hold:** in a scam situation, pay R K Traders. The hold lasts one hour of
   *practice time*. **Skip ahead 1 hour of practice time** moves only that
   practice world's clock. The payment is then checked again and needs an
   explicit "send anyway". Over ₹1 lakh, an analyst must approve the fresh
   check at `/operator/` first.

## Free-tier limits to plan around

- **Sleep:** the service stops after about 15 minutes without visitors. The
  next visit takes about a minute to wake it. Open `/readyz` a couple of
  minutes before judging.
- **Memory:** 512 MB. One process serves everything; the bundle is small.
- **Storage resets:** SQLite lives on the container's disk, so practice
  sessions, pairings and receipts are wiped on every redeploy or restart. For
  durable state, add a Render PostgreSQL database and set `MAYA_DATABASE_URL`.
- **One instance only.** Rate limits and live-stream slots are per process.
- Everything is synthetic: no bank, UPI rail or real money is involved.

## Local check of the same image path

```powershell
.\.venv\Scripts\python.exe scripts/bootstrap_v4.py
.\.venv\Scripts\python.exe scripts/train_wallet_bundle.py
$env:PORT = "8000"; .\.venv\Scripts\python.exe run_demo.py
```

`run_demo.py` binds `$PORT` when it is set, as on Render, and otherwise 8000.
The Docker/Caddy/PostgreSQL route in `docs/DEPLOY_V4.md` still applies to a
self-managed server.
